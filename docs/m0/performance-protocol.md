# OSR-61 — Reproducible performance protocol and M0 calibration

This protocol separates an editor performance promise from measurements of isolated primitives. The M0 executable is a **temporary Rust `String`/WASM/full-DOM calibration**, not the production editor, KWDJ validator, SDK ABI, history engine or serializer. Its results cannot establish the draft budgets of `<1ms core`, `<50ms export` or `400KB gzip` for the future editor.

The architecture owner's current decisions are synchronous main-thread WASM calls after asynchronous initialization, `String` initially, and a full-DOM baseline. Worker ownership or virtualization requires measured benefit and its own correctness evidence. This protocol supplies the measurements for that decision; it does not change those boundaries.

## Reproduction and exact inputs

From the repository root:

```sh
npm ci
npx playwright install chromium firefox webkit
node scripts/m0-perf/capture.mjs
```

CI can run `node scripts/m0-perf/summarize.mjs --check` to verify sealed raw identities, source fingerprints and derived reports without launching browsers, building Rust or writing files. It ignores only the derived summary’s generation timestamp.

The build script requires the recorded `rustc 1.97.1` stable toolchain and the `wasm32-unknown-unknown` target. It fails on a different compiler version rather than silently comparing another toolchain. Cargo builds a dependency-free `cdylib` in release mode with optimization level 3, LTO, one codegen unit, abort-on-panic and stripped symbols. The target cache is outside the checkout; the generated calibration WASM is versioned under `spikes/performance/`. The raw ABI is private to this experiment and does not constrain the SDK contract.

The runner uses its own loopback server on an ephemeral port and isolated headless Playwright browsers. It never attaches to the user's browser profile. Each engine gets three independent browser launches. One launch loads the seven corpora in the documented fixed order, then closes. The page and WASM instance are reused inside a launch: linear-memory capacity and process RSS can therefore retain earlier corpus allocations. This intentionally records a long-lived-session high-water workload, not independently minimized memory for each document. Adaptive payload-copy batches create allocation bursts; process RSS includes this calibration pressure and must not be read as the memory footprint of merely opening a document. Future per-document allocation comparisons also require fresh instances per corpus.

`evidence/osr-61/metadata.json` records the hardware, OS, exact browser/tool versions, base commit, release flags, source hashes, WASM bytes and gzip size. `*-run-*.json` retain raw samples; `summary.json` and `baseline.md` aggregate them. The sequential capture wrapper uses an exclusive capture lock and archives previous raw files before a new series. `series.json` immutably binds metadata and all completed raw files by byte count and SHA-256; sealing also rejects runs outside the metadata→paint time bounds. Summary generation requires the sealed manifest, verifies all baseline/supplement source maps independently and rejects any overlap disagreement. Sources must still match the recorded hashes before a comparison is accepted. Base commit alone is insufficient for a run made from an uncommitted working tree. The checked-in M0 series was captured by running the stages sequentially, then sealed without changing any raw samples; the archive/lock wrapper was added during provenance review for subsequent captures. A failed capture remains evidence. If an interrupted wrapper leaves `capture.lock`, verify that no capture process is still running before removing only that stale lock and restarting; the next attempt archives the partial series.

## Corpus shapes and capacity references

The deterministic generator uses seed `0x61c0ffee`; corpus JSON and private binary buffers have SHA-256 hashes. Generated text contains RU/EN, a multi-codepoint emoji and a combining-mark sequence where the requested leaf size allows a complete pattern. Smaller fixed-width leaves use deterministic ASCII fill. Long fixtures mix RU/EN with emoji/combining sequences; no ASCII-only/Cyrillic-only control isolates text length from shaping cost in this calibration. Every size below is measured from generated bytes, not estimated from character count.

| Corpus | Shape | Main stress |
| --- | --- | --- |
| `long-paragraph` | One 262,144-byte text leaf | Middle insertion/removal, long-line wrapping and native editing |
| `many-small-blocks` | 10,000 paragraphs, 40 UTF-8 bytes each | Node count and repeated layout |
| `deep-tree` | 30 nested quotes, one paragraph and text at depth 32 | Ancestor depth; the kernel edit microbenchmark deliberately does not traverse ancestors |
| `lists` | 50 lists ×100 items, paragraph per item | Structured block layout |
| `table-grid` | 500 rows ×49 columns, no spans; 49,501 structure-plus-text nodes | Table layout near reference row/node limits |
| `near-node-limit` | 50,000 empty structural paragraphs | Node capacity; DOM adds `<br>` caret placeholders, which are not model text nodes |
| `near-byte-limit` | Eight separate 261,000-byte leaves; 2,088,000 total text bytes | Payload, export, copying and text layout near 2MiB |

The first-profile references come from CMS KWDJ v1 at `a7f8a081b7827dd31097ad6c9104654366ae6e04`: normalized document ≤2,097,152 UTF-8 bytes, tree depth ≤32 with root block at depth 1, node count ≤50,000, text leaf ≤262,144 bytes, rows ≤500 and effective columns ≤50. They are **not new generic-core normative caps**. These stress fixtures use a private flat-record format; neither their JSON envelope nor the raw binary is KWDJ. Exact normalized KWDJ validity/counting and the real serializer are NOT_IMPLEMENTED here. Separate near-node and near-byte fixtures avoid pretending that all maxima can be combined into one valid document.

## Measured layers

| Layer | Operation and boundary | Exclusions |
| --- | --- | --- |
| WASM call crossing | Adaptive batch of scalar counter calls; amortized per-call time reported including the JS loop | Payload serialization, document mutation and DOM |
| Core calibration | Adaptive batch of `String` middle insert/remove pairs, divided by the actual batch size | One remaining call amortized over the batch; no tree traversal, validation, selections, history or extension execution |
| Payload crossing/copy | Copy the exported WASM byte range into a new JS `Uint8Array` | JSON/KWDJ decoding and allocation of a production command/result object |
| Export calibration | Rust serializes all flat records into a reusable raw byte vector | Normalization, semantic validation, KWDJ/HTML/Markdown codecs and browser download |
| DOM build + layout | Construct the full DOM, replace the previous root contents, force a layout read | Not the future incremental renderer; the root replacement is an explicit worst-path calibration operation |
| Native typing | Trusted browser key/input events into the native DOM; three warmups then 30 keys | This lane does **not** call the Rust calibration kernel and is not an end-to-end editor input pipeline |
| Startup | Browser launch; WASM fetch/instantiation; corpus fetch/parse/copy/load; initial DOM/layout and second rAF | Loopback network and warm OS caches; no CDN, application shell, Angular integration or real production bundle |
| Memory | Exact WASM linear-memory capacity, plus process-tree RSS sampled every requested 100ms | RSS sums shared mappings and includes runner/server; it is not unique physical memory or an allocator-level peak |

Roundtrip checks compare every output byte before and after the edit-pair workload. Native typing requires exactly 33 inserted UTF-16 units from 33 controlled key presses; after excluding three warmups, all 30 retained key/input samples must be trusted. These checks stop a fast but incorrect calibration run from being accepted.

The timing proxy ends at the second `requestAnimationFrame` after input. It observes a rendering opportunity, **not the screen's physical paint time**, and starts inside the key/input handler rather than at hardware input. The runner also retains browser Event Timing entries when supported, at requested threshold 16ms. Their durations describe an input-to-render interval with 8ms granularity; thresholded entries are censored, so an absent entry is not a zero-duration sample. The raw Event Timing list includes warmup interactions and is reported separately from the 30-key proxy distribution. API support or an empty list must not be converted into a fabricated p99. See the [Event Timing draft](https://w3c.github.io/event-timing/) and [HTML animation-frame processing](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#animation-frames).

The supplemental `paint.mjs` series uses three fresh Chromium launches after the main series finishes. It drains three frames plus 200ms after the last key (outside the measured interval), records handler timestamps from the fixture event trace, and matches unique Event Timing `keydown` entries whose processing interval contains each handler timestamp with ±1ms tolerance. Only complete coverage of all 30 measured keys permits unconditional next-paint quantiles; fast censored cases remain unknown. The supplementary run has its own raw data and source fingerprints; it must not overwrite the main series or combine latencies from different launches.

For release acceptance, OSR-38/OSR-71 must measure the integrated command → Rust validation/transaction → DOM patch pipeline. Use headed installed target browsers and browser-owned Event Timing where available; retain timestamped browser traces/paint checkpoints where unavailable. Include actual RU/EN input, dead keys, selection replacement, undo, paste, joins/splits and long-session edits. Native composition semantics remain gated by the OSR-58/OSR-41 correctness protocol; a CPU microbenchmark cannot replace that work.

## Sampling, noise and regression policy

M0 calibration uses fixed order and no retries. Raw failures remain evidence. Statistics use the nearest-rank estimator `sorted[ceil(p*n)-1]`, with every sample retained:

| Measurement | Warmup samples | Measured samples per corpus/run | Batch size |
| --- | ---: | ---: | ---: |
| Scalar crossing | 10 | 100 | Adaptive; all three calibration probes target ≥5ms |
| Core edit pair | 10 | 100 | Adaptive; same target |
| Export / payload copy | 10 | 100 each | Adaptive; same target |
| Full DOM build/layout | 3 | 20 | 1; yield a frame between samples |
| Native typing proxy | 3 | 30 | 1 key |

For each primitive, double the operation batch until all three probes take at least 5ms (cap 2²⁴ operations), then warm up and collect 100 batch durations. Retain batch counts, calibration probes, elapsed intervals, zero-interval counts and the smallest observed positive timer increment. Divide each batch duration by its operation count. These are amortized throughput measurements, not the latency distribution of individual operations; batching hides individual tails and allocation/GC effects differ from interactive cadence. A cap hit below the target is inconclusive.

Report p50/p95/p99 per run, then the median and range of run p95s and their coefficient of variation (sample standard deviation/mean). Do not pool three launches and call them 300 independent machines. With 20 or 30 samples the reported p99 is simply the observed maximum; it is descriptive and has weak tail confidence. Startup has only three process launches per engine and is similarly descriptive. The final report records the actual maximum interval between RSS samples so delayed sampling is visible.

**Adopted calibration regression policy:** compare identical hardware, toolchain, engine revision, seed, source/build flags and protocol. Interleave baseline/candidate launches (ABBA or seeded order), with at least five launches and ≥200 measured samples for render/input/export when making a gate decision. Fail only if candidate median run-p95 exceeds baseline by both the absolute floor below and `max(20%, 3 × baseline run-p95 CV)`, and the effect repeats in a second independent batch. If baseline CV exceeds 10%, timers are heavily quantized, samples are missing, or the runner/environment differs, mark the result inconclusive and stabilize/rerun; never increase a budget silently.

| Metric | Absolute regression floor |
| --- | ---: |
| Amortized scalar call | 0.0001ms/call |
| String edit pair | 0.01ms/pair |
| Export or payload copy | 0.2ms |
| DOM build/layout | 2ms |
| Handler-to-second-rAF proxy | 4ms |
| Browser Event Timing input-to-next-paint | 8ms, matching its duration quantization; complete measured coverage required |
| Startup | 5ms |
| Sampled process-tree RSS | 32MiB, plus the relative/noise rule; allocator instrumentation needed for production attribution |

These are **measurement guard bands for a regression comparison**, not user-facing latency or memory promises. The 20%/CV rule is a conservative review policy, not a confidence interval or significance test. The absolute floors prevent microscopic changes from triggering architecture work; Event Timing uses its 8ms duration quantum. Change a floor only through a recorded decision with a stable runner comparison. M0's three-run shared-workstation baseline is informational until the controlled comparison requirements above are met. Draft absolute goals remain candidates:

| Draft candidate | M0 disposition |
| --- | --- |
| Core `<1ms` | Not adopted for production: local `String` pairs omit the editor's semantic work |
| Export `<50ms` | Not adopted for production: the private raw export omits real codecs and validation |
| Bundle `400KB gzip` | Not adopted for production: the measured tiny kernel omits the SDK, profiles, renderer and dependencies |

The acceptance artifact should name the target device class, corpus/operation, percentile, sample protocol and exact build. OSR-38 consumes the regression method, OSR-46 consumes measured large-document pressure and correctness gates, and OSR-71 consumes the final integrated release measurements. None should copy a primitive number as a production SLA.

The original WebKit descendant-tree RSS misses XPC processes reparented to launchd, so it is explicitly incomplete. A separate `memory.mjs` launch first requires zero processes from the exact Playwright WebKit bundle, then registers new PIDs with that exact executable prefix while loading all seven corpora and inserting 33 native DOM keys per corpus. This memory-only lane excludes adaptive copy-allocation bursts and 20× repeated rebuilds, so its value does not replace the main workload’s RSS. It includes reparented XPCs, excludes all pre-existing PIDs and system Safari, retains per-process RSS samples and never kills or attaches to user processes. Run this sequentially with no concurrent launch from that bundle. This bounded time-window/executable attribution is not OS audit-token proof; the result remains sampled summed RSS, not unique physical memory or a guaranteed transient peak.

## Worker and virtualization evidence gate

Preserve the full-DOM baseline. Before changing it, compare the same input/corpus traces against a candidate, including serialization/crossing and worker queue delay rather than timing only worker CPU. For virtualization, measure DOM nodes, build/layout, typing latency and attributable memory, and record the candidate's retained/offscreen representation. A useful proposal should show a repeatable reduction beyond the measured runner noise, without moving cost into scrolling, copy/export or startup. Specific required benefit and final architecture remain owner decisions.

Correctness guards include native browser Find, cross-block selection in both directions, drag/keyboard scrolling, copy/cut/paste, focus bookmarks, composition preservation, undo/redo and stable model positions across mount boundaries. Unmounting a composing range or losing offscreen text to native Find fails the candidate regardless of speed. Semantic labels, keyboard access and axe checks remain v1 requirements; real screen-reader support is a separately deferred owner scope and must not be falsely reported as tested.

## Calibration failures and limits

The first Chromium pilot timed out on typing into 50,000 empty `<p>` elements: keydown occurred but no input was inserted. A read-back isolated the fixture problem to missing native caret placeholders. The calibrated renderer now includes `<br>` in empty paragraphs; a repeated single-key probe produced one trusted input and one inserted character. The original partial run and source hashes are preserved under `evidence/osr-61/pilot/`, rather than presented as production editor failure or silently omitted.

A subsequent fixed-batch pilot exposed timer quantization: many short primitive samples were zero. Its three complete Chromium launches and interrupted Firefox launch are preserved under `pilot/quantized/`; the Firefox interruption was an intentional runner termination to revise the protocol, not a browser correctness failure. The accepted calibration uses adaptive batches and retains timing resolution evidence.

Shared workstation load, temperature, power and compositor scheduling were not controlled. Bundled Playwright Chromium/Firefox/WebKit are not interchangeable with installed Chrome/Firefox/Safari release acceptance. Memory is a sampled long-lived-session high-water observation, not a leak verdict. Physical display latency, real production allocator peaks, integrated editing transactions and normalized KWDJ export remain future implementation measurements. The calibration report explicitly labels these unknowns.
